## Context

[0093](0093-a-rule-follows-the-path-it-reads.md) made the builder keep rules and fields in
step, and recorded what it could not cover: a document written by hand, generated by a script
or composed by an agent can carry a rule reading a path no field provides. The roadmap asked
for detection, and the question it asked was whether `validateSchema` should refuse such a
document.

**The first thing to establish was how big the gap actually is, and the paragraph describing
it was wrong.** It said such a document "can be published and nothing refuses it". Measured:

| What the rule reads | At publish |
| --- | --- |
| an unknown **root** — `gone == "8000"` | **refused**, `invalid_logic` |
| an unknown member of a group — `address.nope` | **publishes** |
| an unknown member of a row — `item.nope` | **publishes** |

The root is already refused, because the engine compiles each rule against declarations for
the fields that exist and `Unknown variable: gone` is fatal. What gets through is everything
deeper, because a member of a `map` is `dyn`.

That residual paragraph was written from reasoning rather than from a run, and it was wrong in
the direction that **under-claims the software's own safety** — which is the less obvious half
of this repository's rule about wrong statements. A manufacturer reading it would have built a
check they did not need, and missed the two cases they did.

And the two that get through are the ones that matter: a grouped path is exactly where a
rename leaves a rule behind, because inside a group the data path and the builder's tree path
differ.

## Decision

**Publishing reports it as a warning on a successful publish. It does not refuse.**

Refusing is not available. Tightening what a reader accepts makes documents that are valid
today invalid tomorrow, and the spec versions are frozen — version 1 and 2 and 3 all are. A
reader that starts rejecting a document it used to accept is a worse break than the one
[0051](0051-spec-2-adds-types.md) governs: that is about a *newer* document on an older
reader, where a validation error is the honest answer. This would be an older document on the
same reader.

**`PublishOutcome`'s success variant carries `warnings: readonly string[]`**, always present
and empty when there is nothing to say, so a caller reads a list rather than branching on
whether there is one.

**The route sends them on the `201`**, and omits the key entirely when the list is empty. A
publish that warned has succeeded; a 2xx meaning "partly" is a status no client can handle,
and a client that has never heard of warnings sees the body it always saw.

**Sentences, not codes.** The consumers are a person reading an admin screen, a CLI or a log.
A code would need a catalogue, and nobody would write it.

**The check is a model question, not a type question**, which is why `unknownReferences` is its
own module rather than part of `expressionProblems`. That function asks whether an expression
can ever work and its findings *refuse* the publish; this asks whether the model defines what
a rule reads, and CEL's checker cannot answer that past the first segment. Comparing
`referencedPaths` against `modelDataPaths` answers it at any depth.

## Consequences

**The admin tells success-with-a-warning apart from failure, on screen.** Both are easy to
render as a red line, and a warning that reads as a refusal makes somebody press Publish
again. So the version it created is still announced, and the warnings sit under it in a
politely-announced `status` region — not an `alert`, which would interrupt a screen reader to
report something that is not an error.

**And the two panes stopped wording success differently.** They had drifted to *"published as
v4"* and *"Published version 4."* — the same fact in two voices, invisible to anybody who only
ever uses one tab. `publishProblem` already existed for exactly this force on the refusals;
warnings made it a component, because a success is now a sentence plus a list and a helper
returning a string cannot say that without the callers agreeing on how to split it again.

**A warning is only worth having if it is quiet when it should be.** Five shapes that must not
warn have cases of their own: a group member that exists, a row variable, the row index, a
capability function, `has()`, and a comprehension's own binding. A literal row index —
`items[0].qty` — is normalised to `items[].qty`, because it reads the same field and warning
about it would be a false alarm on valid logic.

**`@formancy/core` is now 17.8 kB brotli against an 18 kB budget**, and the last 0.5 kB is
this check, which no browser runs. It lives in `core` because `core` is the lowest layer that
can see both the spec's model and the expression walker, and because the server and the
builder's authoring check both want it. Recorded in
[§9.3](../architecture/09-quality-requirements.md) rather than hidden: the next thing added to
that package should either be under 0.2 kB or arrive with a decision about splitting the
barrel.

**It is a report, and a manufacturer who needs a gate has to build one.** The API returns the
warnings on the `201`, so it is mechanisable — but nothing in formancy fails a pipeline over
them, and `SAFETY-ANALYSIS.md` B1a says so as the main residual rather than as a footnote.

**There is still no detection pass over documents already published.** The warning is computed
from the document being published, so a form that went out before this existed is not
revisited.

## Alternatives considered

**Refuse it in `validateSchema`.** Rejected on the contract, above — and the cost would land
on the builder first, since `createBuilderSession` throws on a document the validator rejects.
A form published a year ago with such a rule would stop opening in the editor, which is the
worst possible way to deliver this news.

**Refuse it at publish only, leaving `validateSchema` alone.** Tempting, because publishing
already refuses four other things and a published version is frozen forever, so this is the
last moment anybody can act. Rejected because of what it does to the *existing* corpus:
republishing an unchanged document is a supported no-op, and a deployment that redeploys its
forms from source would find a form it published last month now unpublishable, with no change
on their side.

**A new spec version that forbids it.** Rejected as the wrong instrument. A version is a
reader contract about what constructs *exist*; this is a consistency rule between two parts of
one document, and expressing it as a version would mean a version-4 reader refusing a
version-3 document that a version-3 reader accepts — for a reason that has nothing to do with
vocabulary.

**Report it through the existing `invalid_logic` channel with a flag.** Rejected: the channel
is a refusal and its callers treat it as one. Threading "but this one is advisory" through a
refusal type is how a client ends up treating a real refusal as advisory.

**Compute it at render instead, so a form already out there reports too.** Rejected on the
same ground [0093](0093-a-rule-follows-the-path-it-reads.md)'s own predecessor used: a form
somebody is halfway through filling in must not start failing to open. A renderer has nobody
to tell either — the person filling the form in cannot fix the schema.
