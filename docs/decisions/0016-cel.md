# 0016 — Use CEL for conditional logic and calculations

- **Status:** accepted
- **Date:** 2026-09-19
- **Deciders:** Daniel Bacher
- **Verified by:** `packages/expressions/src/cel-spec-corpus.test.ts` runs the
  official CEL conformance corpus through formancy's own facade and counts every
  exclusion ([0036](0036-pin-the-cel-corpus.md));
  `packages/expressions/src/check.test.ts` rejects `age > "eighteen"` at check
  time — "rejects comparing an int against a string before the form is saved";
  `packages/spec/src/csp.test.ts` asserts the shipped validator source contains
  no `new Function` and no `eval(` ([0040](0040-no-eval.md)).

## Context

A form's visibility, requiredness, calculation and cross-field validation rules
are authored by users, stored in the schema, and evaluated twice: in a browser
while someone fills the form in, and again on a server when the submission
arrives ([0006](0006-one-engine-build.md)). The language those rules are written
in settles two questions at once. It settles the threat model, because a schema
is user-authored content that a server will execute. And it settles whether a
form's dependency graph can be known before anyone uses that form, because only
a language whose references can be read off its syntax can be analysed ahead of
time.

## Decision

Conditional logic, computed values and validation rules are written in CEL, the
Common Expression Language. Nothing else in a schema is executable.

## Consequences

**What it buys.** The reasons compound. CEL is non-Turing-complete by
construction — no loops, no recursion, termination guaranteed by the grammar
rather than by a sandbox bolted on afterwards. Kubernetes CRD validation, Envoy
and Firebase Security Rules run on it against an identical threat model, so the
shape of the answer is not being invented here. It is typed and has a
compile-time checker, so a comparison between an int and a string is refused in
the builder instead of surfacing the day a user reaches that field. Its AST
yields exact static variable references, and that single property is what makes
[0018](0018-static-dependencies.md) possible at all; a JavaScript sandbox cannot
say what a program will read. It is readable, so a schema diff is reviewable in
git by the person who wrote the rule. And the language is specified
independently of any implementation, so a Go or Java implementation of the same
open schema stays possible, which matters because
[0006](0006-one-engine-build.md) pins the current server to Node.

**What it costs.** Authors cannot write arbitrary code, and some things are
genuinely awkward to express with no statements and no way to define a helper.
The escape hatch is placed deliberately outside the expression language:
server-side action scripts are the one place a general language is allowed, off
by default and behind an explicit flag. Never in the expression language, and
never in the browser.

## Alternatives considered

**JSONLogic.** Rejected: unreadable for authors once a rule grows past one
comparison, and untyped, so nothing catches a mistake before a user does.

**expr-eval.** Rejected: unmaintained since 2019.

**jsep.** Rejected: a parser and nothing else. The semantics, the type system
and the security properties would be ours to own forever.

**QuickJS or isolated-vm.** Rejected: 500kB to 1MB of WebAssembly shipped to a
browser in order to evaluate `age >= 18`. What that buys is containment of a
general language, rather than a language that needs no containment.
